# 回复助手架构

## 运行链路

整个仓库即标准 Skill：根 SKILL.md 为唯一入口，根 src 为唯一业务源码，scripts 为管理和发布工具，docs 为说明。bundle.py 只枚举公开资源白名单；build_skill_bundle.py 生成根清单，可导出仓库外干净安装源，不在仓库内生成代码副本。校验安装产物时使用 strict 模式，拒绝额外私有文件。

已有根项目直接沿用配置、.venv、账号和队列，管理入口支持未登记的原项目，不另建 instance.json 改变运行身份。新部署可原地初始化，也可指定独立数据目录；独立目录只保存一份 runtime 程序，自启复用其中的管理脚本，不再复制完整 management 包。旧 management 自启入口升级后转发到 runtime。`lifecycle` 使用 Windows 内核 PID 与创建时间核对进程身份；主循环每两秒原子记录心跳、账号状态和子进程身份。管理查询使用十五秒新鲜度阈值，不以数据库遗留 ONLINE 推断运行状态。旧入口继续受原 bridge.lock 保护，结构调整不自动迁移或重启服务。

`management_probe` 在实例解释器内做只读配置与数据库摘要，管理启动时也通过它统一 .env 优先级；原 CLI 的环境变量优先规则保持不变。管理命令只在新 init/独立实例 upgrade 安装依赖，用 uv.lock 锁定环境；独立实例采用非编辑安装。已有根项目 init 不修改环境，upgrade 拒绝覆盖自己的源码目录。独立实例升级先在 backups 下验证候选环境，再取得原实例锁，保存 SQLite 一致性快照，保留旧运行资源与环境。具体命令、版本门槛和验收边界见 [Skill 验收记录](skill-validation.md)。

`goofish_bridge.__main__` → `supervisor` → 每账号独立 `account_worker`。

Windows 管理启动使用 `CREATE_NO_WINDOW | CREATE_NEW_PROCESS_GROUP`，标准输入为空设备，输出重定向到本机日志。不能用 `DETACHED_PROCESS` 代替无窗口标志：本项目虚拟环境启动器在该方式下会创建控制台。生命周期回归通过真实 Windows 进程核查主进程与 spawn 子进程的控制台句柄均为零，并检查启动命令返回后的存活、重复启动和安全停止。

闲鱼入站由 `goofish_adapter` 与 `messages` 解析，经主进程落库后，通过 `feishu_adapter` 转发。本人飞书卡片或引用回复经 `router` 精确定位账号、客户、会话，由 `store` 持久化并排队，再由对应账号进程发送。

## 保留模块

- `account`、`config`、`network`、`bitbrowser_cookie`：账号隔离、身份校验、独立出口、凭据获取和刷新。
- `goofish_cli/core` 与 `static/goofish_js_version_2.js`：会话、签名、Token、协议、限流、风控和异常。
- `messages`、`router`、`store`：消息归一化、固定路由、会话记录、去重、任务生命周期和恢复。
- `account_worker`、`supervisor`、`feishu_adapter`：同连接收发、进程管理、飞书事件和投递。
- `probe_store`、探针命令、测试与启动脚本：协议排障、回归验证和运行支持。
- `goofish_cli/commands/auth`、`commands/message`：独立诊断入口，使用 registry 自动发现。

账号、客户及会话由确定性代码和持久化映射选择。发送结果未知时不自动重发。正式业务数据库及其 WAL 不属于可清理缓存。

## 账号网络与客户端声明

启用 `bitbrowser.enabled` 后，`run` 在单实例锁内先读取指定分组的全部分页窗口，再按 Cookie `unb` UID 与配置及磁盘绑定去重，补建本地账号；账号编号支持 A1、A2…，不再限制三个。已有账号保留编号、绑定和历史路由，同 UID 多窗口只使用一个来源，同名不同 UID 独立建号。未绑定的同名预留槽位可复用，已有窗口切换 UID 时停止同步，禁止自动改绑。未登录或凭据读取失败的窗口记录警告后跳过，本地已有账号不因窗口缺失而删除。

发现结果写入各账号 `accounts/A*/account.json`，配置装载时合并，子进程也读取同一份记录，不改写用户 YAML。凭据沿用原加密保存流程，重复同步不覆盖已有 Cookie；元数据先原子保存，凭据保存中断时下次同步可继续。绑定窗口 ID 后，凭据、代理和 UA 均按该 ID 在原分组内定位；未同步的旧账号仍按名称定位。`sync-accounts` 可仅同步，使用与运行相同的单实例锁；默认 `run` 启动同步后的全部已绑定账号，`--accounts` 可限制启动范围。当前在启动或显式命令时同步，不在运行中热添加进程。

启用 `bitbrowser.enabled` 时，优先按分组和已绑定窗口 ID 唯一定位窗口，旧账号未绑定窗口 ID 时按名称定位，校验其 Cookie UID 与本地绑定相符，从同一窗口 `/browser/detail` 读取代理及 `browserFingerPrint.userAgent`。窗口配置是唯一来源，忽略手工 `network` / `client`，不需要维护代理环境变量。只有明确 `proxyType=noproxy` 才直连；支持自定义 HTTP、HTTPS、SOCKS5 和认证，动态提取、全局代理、SSH、缺失字段或读取失败均拒绝，不用旧地址猜测。Cookie 和运行配置在 load_session 时一次获取，避免入口与 Worker 构造重复刷新。

未启用比特来源时，保留 `network.mode=direct/proxy` 和 `proxy_url_env` 手工方式。HTTP Session 和 WebSocket 连接工厂共用同一个 NetworkProfile，监听、收发、历史查询及重连不另选出口；窗口修改在重启账号进程后生效。SOCKS5 统一为 socks5h，由代理解析目标域名；代理失败不回退直连。飞书继续直连。PySocks 和 python-socks 分别服务于 HTTP 与 WebSocket；websockets 限定 15.x，锁定 15.0.1，特殊字符认证通过隔离连接子类解码，不修改第三方模块全局函数，保持 HTTPS 代理及目标 WSS 的 TLS 验证。

HTTP 请求头、WebSocket 握手和 IM 注册共用一个 ClientProfile，Client Hints 和 IM 附加版本信息由 UA 派生。比特来源使用窗口 UA，其他来源可显式配置 Windows/macOS/Linux 桌面 Chrome UA，未配置时默认 Windows 10 / Chrome 133。独立扫码保留真实 Chrome 声明，仅应用账号网络；带认证的 SOCKS5 应在原比特窗口登录，独立扫码入口明确拒绝。程序只读比特代理和指纹字段，不改写窗口配置，不自动轮换代理或指纹。

`device.json` 是程序自身的稳定 IM 设备 ID，按账号路径显式读取，并同时用于 Token 获取和 IM 注册。已有 ID 不因代理、UA 或 Cookie 更新而重建；不导入、覆盖为比特设备指纹。Cookie 导入仅携带 Cookie 记录，不包含完整浏览器指纹、localStorage 或浏览器网络栈。统一客户端声明不等于复制浏览器设备环境，也不保证平台风控结果。

## 后续 AI 接入边界（尚未实现）

可在入站消息持久化后生成建议正文，交由本人确认。模型只生成正文，不选择或改写账号、客户和会话目标；确认后的发送继续经过身份校验、固定路由、持久化队列和限流。

会话记录可作为上下文来源，但后续仍需设计商品知识、模型配置、上下文范围、人工接管、草稿状态及发送前的新消息检查。当前没有实现这些 AI 能力，不引入占位模块或额外模型依赖。

## 裁剪范围

移除商品管理、搜索、分类、地址、独立图片上传命令、MCP、插件、技能安装、宣传素材及上游发布工作流。保留认证、消息诊断和全部消息桥基础设施。图片回复专用上传由 `goofish_bridge.media` 提供。

## 图片回复（2026-09-20）

飞书只接收绑定本人的私聊 `image` 消息，以 `parent_id` 固定定位原账号、客户、会话，不使用 `root_id` 兜底。`reply_tasks` schema 升级到 4，新增 `message_type`（旧任务默认 text）和 `image_key`；保留原飞书消息 ID 作为幂等身份，卡片文字提交继续走原路径。

账号 Worker 在原串行发送任务中调用 `media.prepare_image`，通过线程执行网络和图片验证，避免阻塞 WebSocket 接收。飞书凭据通过固定直连接口换取 tenant token，再按消息 ID 和 image key 流式下载，图片只驻留内存。PNG、JPEG（包含 .jpg/.jpeg）按实际内容校验，限制静态单帧、10 MiB、2500 万像素，不主动重编码。随后使用目标账号 Session 向闲鱼上传，继承账号 Cookie、代理和 UA，检查响应状态、图片 URL 和尺寸，再通过原 IM 连接发送 `custom.type=2` / `contentType=2` 图片消息。

下载、上传在任务领取后完成，后续文字不会越过正在处理的图片任务。上传完成后重新检查过期、连接及风控。图片准备失败为 FAILED，发送请求后的超时为 UNKNOWN；进程中断的 DISPATCHING 任务仍保守恢复为 UNKNOWN，不自动重发。图片资源标识持久化，二进制及上传地址只在本次任务内存中，不创建媒体磁盘缓存。已排队且尚未领取的任务重启后可以重新下载；领取后的任务需要人工核对，不宣称跨崩溃断点续传。

图片异常回执显示经过媒体模块脱敏的失败原因。2026-09-20 安全重启后，用户确认图片发送测试成功；未分别报告全部格式、大小边界及多图场景的真机结果。自动测试模拟外部接口。仅返回服务端接受不等于买家实际收到。

## 客户图片转发到飞书（2026-09-22）

闲鱼实时轻量推送中的 `[图片]` 只有摘要，账号 Worker 先按原路径保存摘要并提醒，再按会话和源消息 ID 补拉历史。真实历史样本为 `contentType=101` 的 custom 包装，base64 负载中 `contentType=2`，`image.pics` 含图片 URL 和尺寸；仅接受单张、HTTPS `img.alicdn.com` 地址。历史记录与摘要使用同一源消息 ID，数据库对已有摘要补齐 `message_type=image`，并以入站消息 ID 创建唯一图片投递任务；不重复创建客户卡片或文字提醒。

图片任务在原客户卡片建立后领取。发送线程从固定图片 CDN 流式下载，拒绝重定向，限制 10 MiB，并按实际内容验证静态 PNG/JPEG/WebP 和 2500 万像素；闲鱼 CDN 返回的静态 WebP 在内存中转为 JPEG，带透明通道时转为 PNG。飞书先上传图片取得 `image_key`，再作为图片消息直接回复原客户卡片；该飞书消息 ID 关联原入站消息，直接引用图片也能回到冻结的闲鱼账号、客户和会话。图片下载或上传失败保留原 `[图片]` 文字提醒，图片任务记为失败并向本人发送原因；图片消息请求结果不确定时保留 UNKNOWN，提醒人工核对，不自动重发。图片字节只驻留内存，URL 保存在已有投递队列中供崩溃恢复。飞书应用需要 `im:resource` 图片资源权限；实测缺少该权限时上传接口返回 `99991672`。

比特 Cookie 读取先解析响应，再检查关键字段、H5 Token 一分钟有效余量及同名冲突。实时接口为空（包括 cookies/list 包装的空集合）、不完整、过期、冲突或读取失败时，查询原绑定窗口状态；窗口仍在运行则通过 CDP 整组读取闲鱼 Cookie，最多读取五次、间隔一秒，等待页面自行完成加载，不导航、新建页面或关闭用户窗口。读取前再次检查运行状态，停止或无法确认时终止；仍无有效凭据时报告获取失败，不据此认定浏览器退出登录。UID 校验在读取后照常执行。

实时接口、同步快照、CDP 读取及无头刷新统一保留 partitionKey 并筛选：优先闲鱼顶层站点 https://goofish.com 分区中的同名字段，其余字段使用非分区 Cookie；排除其他站点分区。仍有同名冲突则拒绝，不按顺序或令牌到期时间拼接签名字段。仅确认窗口已关闭且实时接口正常返回时才使用快照或原窗口无头刷新；实时接口异常且窗口已关闭时保留原异常，不自动打开窗口。
