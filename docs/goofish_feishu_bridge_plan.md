# 闲鱼三账号 × 飞书双向消息桥：完整方案与最小 MVP 实施计划

版本：v1.0
整理日期：2026-09-19
目标环境：本地 Windows 电脑 + 手机飞书
基础仓库：`https://github.com/fancyboi999/goofish-cli`

> **最终决定：首版支持三个闲鱼账号，全部使用本地直连；每个账号独立保存登录态、独立运行。通过一个飞书应用机器人接收客户消息，由本人引用消息回复，程序准确转发回原账号的原客户。代理模块只预留配置和接口，不作为 MVP 的实施前置条件。**
>
> 本文是待开发的实施方案，不是已经完成的系统。仓库结论来自整理时公开 `main` 分支的关键源码核对，未使用真实账号进行联调；三账号同时在线、移动端引用事件、断线补拉范围等必须通过下述测试确认。文中的新增模块、配置项和消息桥命令均是拟开发接口，不是上游仓库已提供的功能。

## 1. 项目目标与使用方式

在本地登录三个自有闲鱼账号。出门后，任何一个账号收到客户消息，程序自动推送到本人手机上的同一个飞书机器人；本人引用对应消息输入回复，程序将文字原样发送到正确闲鱼账号的正确会话。

系统是消息转发工具，不是 AI 客服。消息匹配、权限校验、去重和发送均由确定性程序完成，不调用大模型，不需要 Hermes、MCP 或多 Agent 编排。

### 1.1 收到客户消息

飞书推送示例，以下名称、ID 和时间均为示意：

```text
闲鱼新消息 · #A2-00128

账号：A2｜软件销售号
账号ID：123456789
客户：小张
客户ID：987654321
消息：这个软件支持自动发布吗？
消息时间：2026-09-19 14:32:08

请引用本条消息回复。
```

必须展示账号编号、账号ID、客户ID和消息内容。账号昵称、客户昵称能取得则展示，缺失时显示“昵称未知”，不能编造；缺少必要路由信息时只能推送异常提示，不能开放回复投递。

### 1.2 在飞书回复

本人在飞书里长按上面的机器人消息，使用“回复”功能，输入：

```text
支持的，目前可以发布商品笔记。
```

程序根据被引用消息的飞书消息ID查询已保存映射，向 A2 账号的对应客户发送正文。无须手动输入账号ID或客户ID，也不需要切换三个机器人。

飞书回执使用清楚的状态描述，例如：

```text
回复任务 #R-00036
账号：A2｜软件销售号
客户：小张｜987654321
正文：支持的，目前可以发布商品笔记。
状态：闲鱼服务端已接受发送请求。
```

“已排队”“服务端已接受”“明确失败”“结果待确认”必须区分。不能一收到飞书回复就显示“发送成功”。

### 1.3 首版交互边界

首版只允许引用机器人转发的原客户消息进行文本回复。不引用、引用自己的回复、引用机器人状态通知或任意其他消息，都不触发闲鱼发送。连续追加回复时，再次引用原客户消息即可。

发送给机器人但未引用消息的“状态”作为唯一管理查询入口，返回三个账号状态、待发送数量和异常任务数量；其他未引用文本提示正确回复方法。**带引用的“状态”视为准备发给客户的普通正文，不解析成管理命令。**

## 2. 最小 MVP 范围

**MVP 最终交付是三个账号，而不是一个账号。单账号联调只是开发顺序中的第一步。**

| 维度 | 首版必须完成 | 暂不实施 |
|---|---|---|
| 账号 | 3 个自有账号，独立登录态、独立进程、身份校验 | 账号池、批量注册、账号售卖 |
| 网络 | 三账号本地直连，统一网络配置入口 | 代理连接实现、代理采购、独立公网 IP 验收 |
| 闲鱼接收 | 实时文本、轻量通知补正文、其他可识别消息类型提示 | 图片和文件下载、语音转文字、视频解析 |
| 飞书交互 | 1 个自建应用机器人、本人私聊、引用回复 | 群聊、多客服分配、复杂消息卡片 |
| 闲鱼发送 | 本人输入的纯文本，发往已有会话 | AI 自动回复、图片和文件发送、主动新建客户会话 |
| 可靠性 | 固定映射、持久化任务、去重、发送状态、重连与有界补拉 | 无限历史同步、完整聊天记录管理后台 |
| 运维 | 本地启动/停止、状态查询、账号异常提示、开机或登录自启配置 | 云服务器部署、容灾集群、远程监控平台 |

非文本消息不能因为没有正文就静默丢弃。首版可以显示“客户发送了一张图片，请到闲鱼查看”；未知格式显示“收到暂不支持解析的消息”。只有账号、会话、客户信息完整且可信的提示，才允许作为文本回复入口。

三个账号直连意味着它们使用同一套本地网络，**不承诺独立出口 IP**。首版解决的是账号数据隔离和消息准确路由，不是网络身份隔离。

## 3. 技术架构

### 3.1 部署结构

```text
本地 Windows 电脑
│
├─ 消息桥主进程
│  ├─ 飞书长连接事件接收
│  ├─ 飞书消息发送与回执
│  ├─ 身份校验、引用路由、任务调度
│  ├─ SQLite 持久化与恢复
│  └─ 三个账号进程的启动、停止与状态监督
│
├─ 账号进程 A1 → A1 独立登录态 → 本地直连 → 闲鱼
├─ 账号进程 A2 → A2 独立登录态 → 本地直连 → 闲鱼
└─ 账号进程 A3 → A3 独立登录态 → 本地直连 → 闲鱼

消息桥主进程 ↔ 飞书平台 ↔ 本人手机飞书
```

建议使用 Python 3.12、上游仓库的闲鱼协议能力、飞书官方 `lark-oapi` SDK 和 SQLite。上游声明 Python 最低版本为 3.11；具体依赖必须在联调后锁定，不追随浮动的最新版本自动升级。[^deps][^sdk]

飞书使用自建应用的长连接事件接收方式，不采用需要对外暴露本地服务的 HTTP 回调方案，因此本项目无需配置公网入站地址、域名或内网穿透。[^feishu-ws]

### 3.2 最小模块划分

| 模块 | 单一职责 |
|---|---|
| `account_worker` | 一个进程只负责一个账号的认证、监听、发送和补拉 |
| `goofish_adapter` | 封装上游协议、事件解析和异常转换，不处理飞书业务 |
| `feishu_adapter` | 接收飞书事件、发送转发消息和回执 |
| `router` | 校验引用关系，生成不可变的发送目标 |
| `store` | 消息、映射、任务、账号状态和补拉进度的持久化 |
| `network` | 统一创建网络连接；首版只实现直连 |
| `supervisor` | 管理进程生命周期、状态和恢复 |

一个代码仓库、一套虚拟环境、一个 SQLite 文件、三个账号目录即可。不引入 Redis、Celery、FastAPI、网页管理后台或微服务拆分。

主进程集中管理数据库写入；账号进程通过本地进程通信提交事件和接收任务。进程间队列只是通信通道，不是可靠存储：只有 SQLite 提交完成，才视为本地接收完成。

飞书 SDK 事件回调只负责校验和快速落库，不能等待闲鱼发送或历史补拉。阻塞网络调用也不能堵住账号监听和心跳。

## 4. 基础仓库的复用方式与必要改造

### 4.1 可以复用的能力

上游提供 Cookie 导入、扫码登录、会话查询、历史消息、实时监听、文本发送以及限流和风控保护等基础能力。它适合作为闲鱼接入层，不等于已经具备本项目所需的多账号飞书消息桥。[^repo]

建议 fork 仓库，在同一仓库新增 `src/goofish_bridge/`。只对上游模块做必要修补，不将飞书逻辑散落到上游各命令里。开发启动时记录实际使用的 commit SHA，并将 Python 与依赖版本写入锁文件；升级需要重新跑测试。

### 4.2 关键差距与改造要求

| 核对结果 | 本项目改造要求 |
|---|---|
| Cookie 读取支持 `GOOFISH_COOKIES_PATH`，但设备缓存仍有用户目录默认路径；登录命令写入目标仍使用默认 Cookie 路径。[^session][^login] | 登录、读取、刷新、缓存统一使用当前账号的数据目录，不能只修改 Cookie 读取路径 |
| IM Token、限流和风控状态各有用户目录下的公共文件路径。[^token][^limiter][^guard] | 逐一纳入账号目录；禁止多个账号共享可变状态文件 |
| 文本解析输出没有保留完整消息ID、时间；历史整理也丢失部分元信息，历史查询持续翻页。[^ws] | 保留经实测确认的消息身份和时间，增加分页上限、超时、停止条件 |
| 存在 `new_msg` 轻量通知，需要进一步获取正文；监听注册校验需要补强。[^ws] | 通知补正文、连接就绪判定、监听活性检测和补拉均纳入适配层 |
| 当前发送路径另建连接；监听路径先 ACK 再调用业务处理。[^send][^ws] | 测试收发是否互相影响；缩小确认与落库之间的丢失窗口 |
| `message send` 的 `ok=true` 仅表示服务端接受请求。[^send] | 保留真实发送状态，不把接受回包当成客户已收到 |
| 默认本地写入限制为每分钟 1 次。[^limiter] | 首版保留保护并按账号排队，不将此数值宣传为平台安全额度 |

### 4.3 不直接照搬 CLI 循环

首次技术验证可以使用 CLI 命令。但正式消息桥需要结构化异常、原消息ID和发送阶段信息，不能仅靠读取终端上的成功/失败文字判断状态。

发送必须区分“请求尚未发出”和“请求可能已发出但回包丢失”。上游将不同情况转成异常时，适配层需要保留发送阶段，不能将所有异常都当成可重试失败。

可以先保留“常驻监听连接 + 按需发送连接”的实现来缩小改造范围。**只有实测确认两者共存稳定，才能用于 MVP。** 若另建连接会打断接收，改为一个账号复用连接，并由唯一接收循环按请求ID分发回包与推送；不能让两个协程同时消费同一 WebSocket。

## 5. 三账号隔离与本地直连

### 5.1 账号隔离规则

固定使用 A1、A2、A3 作为本地编号，每个编号绑定一个经过本人确认的闲鱼 UID。账号显示名只是备注，不参与路由。

每个账号拥有独立的 Cookie、设备缓存、IM Token、浏览器登录/刷新状态、限流记录和风控状态；属于同一账号的所有读取与写回必须使用同一路径。账号目录不等于设备或虚拟机隔离，本项目不承诺平台不会关联账号。

统一新增 `AccountPaths` 路径对象，根据 `account_key` 计算目录。建议优先显式传递对象，而不是在运行中反复修改全局变量；确需兼容上游环境变量时，也只能在独立子进程启动时设置，不能在多个账号线程之间切换。

启动、重新登录、凭据刷新后以及发送前，都要校验当前会话 UID 与该账号绑定 UID 一致。发现不一致立即停用此账号，其他账号继续运行。

**不允许把旧 A1 直接重新绑定到另一个闲鱼 UID 后继续消费旧任务。** 更换账号必须关闭旧绑定和旧待发送任务，重新初始化；路由记录中的原 UID 不得被覆盖。

上游在 Cookie 缺失时可以从本机浏览器自动探测账号。后台模式应设置已有的 `GOOFISH_NO_CHROME_BOOTSTRAP=1`，同时审查其他浏览器刷新路径，禁止它们悄悄加载另一个账号。[^session]

### 5.2 初次登录流程

逐个初始化 A1、A2、A3。使用明确指定账号的 Cookie 文件导入，或者由该账号专属登录流程扫码；不要自动抓取“本机第一个可用浏览器账号”。

每次登录显示实际 UID 与可获得的昵称，由本人在本地确认绑定，再保存凭据。后续启动不要求浏览器窗口一直打开，但是否需要浏览器辅助刷新以及账号会话能保持多久，都以该账号实测为准，不承诺永久在线。

人工重新验证、扫码、处理验证码可以在本地完成；首版不远程自动操作验证，也不绕过平台风控。

### 5.3 首版网络模块

首版为全部账号配置：

```yaml
network:
  mode: direct
  proxy_url_env: null
```

`NetworkProfile` 和统一连接创建入口在首版建立，但 `proxy` 模式暂不实现。配置了未支持的代理模式，应明确报“功能未实现”并停止该账号，不能无声退回直连。

直连不等于“不填代理地址就完成”。Requests 会受环境代理配置影响；支持代理参数的 websockets 版本也会自动读取环境或系统代理。应在适配层显式关闭代理继承，例如 Requests 设置 `trust_env=False` 并清空代理，WebSocket 使用经依赖版本确认可用的 `proxy=None`。[^requests][^websockets]

浏览器登录路径也要明确使用直连配置；飞书的 HTTP 和长连接分别核查，不假设改了闲鱼 Session 就能影响飞书 SDK。

**应用层关闭代理无法覆盖操作系统路由、Clash TUN 或其他透明转发。** 部署时应检查这些设置，将消息桥实际访问路径配置为 DIRECT，或在关闭相关转发的环境完成直连验收。不要为了此项目全局修改其他开发工具的代理。

网络模块只控制连接策略，不包含账号选择、客户匹配或消息路由。后续增加代理时不应重写业务模块。

## 6. 飞书机器人配置与安全回复规则

### 6.1 应用类型与权限

新建独立的飞书自建应用，例如“闲鱼消息助手”，开启机器人能力。它不是仅能接收推送的群自定义 Webhook，也不与其他 AI 机器人共用消息处理链路。

使用官方 SDK 长连接接收 `im.message.receive_v1`。权限最小化：接收本人发给机器人的私聊消息，以及以应用身份发送消息；对应权限包括 `im:message.p2p_msg:readonly` 和 `im:message:send_as_bot`。发布版本并配置本人可用范围，实际权限效果在应用内验证。[^feishu-ws][^permissions]

`im.message.receive_v1` 是事件名称，不是权限名称；两项要分别配置。首版无需通讯录读取、云文档、多维表格、群消息全量读取等权限。

飞书 App Secret 由本地环境变量或受限配置加载，不放进代码、普通 YAML、日志或 Git。使用中国版飞书服务配置，不混用海外 Lark 的应用凭据和服务端点。

### 6.2 绑定本人身份

首次启动采用本地主动发起的绑定流程：本人向机器人发送一条测试消息，本地显示事件中的 `open_id` 和 `chat_id`，由本人明确确认后写入白名单。不能自动信任第一个给机器人发消息的人。

正常运行同时检查应用/租户、发送者类型、允许的 `open_id`、绑定私聊 `chat_id` 和消息类型。非本人、其他聊天、机器人自身事件均不得触发闲鱼发送。

### 6.3 固定路由映射

```text
机器人转发消息的飞书 message_id
    ↓
account_key + 绑定的闲鱼账号 UID
    ↓
原闲鱼会话 cid + 客户 UID
    ↓
原闲鱼消息ID
```

飞书官方事件模型包含 `message_id`、`parent_id` 和 `root_id` 等字段。首版只使用经过联调确认的直接引用 `parent_id` 查映射；不能在查不到时随意用 `root_id`、最近客户或昵称兜底。[^event-model]

所有账号ID、客户ID、会话ID、消息ID都按字符串存储，不转成数字。会话ID是否带协议后缀，由适配层按照真实协议统一处理，不能在各模块分别拼接。

同一客户联系 A1 和 A2 时，属于两条不同路由。即使两个客户同名，也不能依赖昵称合并会话。

发送目标在任务创建时完整冻结，执行前再次校验账号绑定。客户文字、飞书引用展示文本、人工备注，都不能覆盖数据库中的目标字段。

## 7. 消息处理流程

### 7.1 闲鱼 → 飞书

```text
接收闲鱼推送
→ 解析整帧内的全部事件
→ 确认属于哪个本地账号
→ 区分客户消息、本人消息、系统事件和轻量通知
→ 补全消息ID、会话、发送者、正文和时间
→ 去重并持久化
→ 同一事务创建飞书待投递任务
→ 向本人飞书私聊发送
→ 保存飞书 message_id 与原消息映射
```

消息身份优先使用真实源消息ID。底层请求 `mid`、客户端 UUID、平台消息ID不是天然等价的字段，必须分别保存。具体字段路径从真实样本确认，不按名称猜测。

收到 `new_msg` 时，按通知里的会话和消息身份补拉正文；如果正文先到，后到的通知只用于补充元信息，不再重复推送。针对同一会话的并发补拉请求应合并。

同一帧中存在多条消息时必须全部处理。识别为当前账号自身发送的消息，只用于状态核对，不再伪装成客户新消息推送；也不能靠“正文与刚才回复一样”就判断为本人消息。

缺少稳定消息ID时先等待关联或有限补拉。仍无法建立可信身份的事件保留异常记录并提示，不使用“客户ID + 正文”冒充可靠去重键。普通文本的稳定身份提取是联调验收项；做不到就不能宣称可靠收消息已完成。

消息时间与本地收到时间分别保存。源时间缺失时标明“收到时间”，不能把本地时间冒充客户发送时间。补拉消息标记“离线补收”，避免被误认为刚刚发生。

对业务消息，改造目标是尽可能在本地持久化后再确认处理，协议要求必须实测。若无法改变上游 ACK 时序，必须保留该故障窗口并用重连补拉覆盖，不能宣称绝对不丢消息。

### 7.2 飞书 → 闲鱼

```text
接收飞书消息事件
→ 校验本人身份和绑定私聊
→ 按飞书 message_id 去重
→ 要求纯文本且直接引用已知客户转发消息
→ 查询完整固定映射
→ 校验账号 UID、会话和客户
→ 持久化回复任务及原文
→ 对应账号按顺序取出任务
→ 再次校验账号、在线状态与任务有效期
→ 按限流规则发送
→ 保存发送阶段、请求标识和回包
→ 在飞书反馈真实结果
```

飞书官方要求有幂等需求时使用 `message_id` 去重，不依赖 `event_id`；同一条回复事件重投不能创建第二个发送任务。[^feishu-event]

本人分别发送的两条相同正文具有不同飞书消息ID，应视为两个独立操作，不能仅按文字相同合并。

正文按收到的纯文本原样发送，只做空内容、类型和长度校验，不加 AI 改写、不加账号前缀、不自动附带签名。遇到不支持的富文本、图片、文件或超长文本时明确拒绝；首版不静默截断，也不自动拆成多条客户消息。

只允许向已有映射的会话回复。禁止通过参数兜底新建会话、替换客户，或根据商品ID重新寻找目标。

### 7.3 发送状态与重复发送防护

| 状态 | 含义 | 自动处理 |
|---|---|---|
| `QUEUED` | 已持久化，尚未尝试发送 | 在线且未过期时进入账号发送队列 |
| `DISPATCHING` | 已准备发出或正在等待发送结果 | 记录请求标识，不允许另一执行者重复领取 |
| `SERVER_ACCEPTED` | 收到明确的服务端接受回包 | 发送对应飞书回执；不宣称客户已读 |
| `FAILED` | 明确未发送或服务端明确拒绝 | 反馈原因；仅对确认无副作用且可恢复的错误安排有限重试 |
| `UNKNOWN` | 可能已发送，但没有可信结果 | 暂停自动重发，核对历史或交由本人确认 |
| `EXPIRED` | 未发送任务超过有效期 | 不再自动发送，提示重新引用原消息提交 |

在真正发出请求前，保存客户端请求标识及 `DISPATCHING` 状态。程序重启时残留的 `DISPATCHING` 不能直接改回 `QUEUED`，应进入 `UNKNOWN` 并核对。

即使客户端可以固定 UUID，也不能未经验证就认定闲鱼服务端会按它幂等。历史核对优先使用平台消息ID或已验证的关联字段；只有“正文相同、时间接近”不足以自动认定成功。

本项目目标是：有状态、有去重、未知不盲发。**不承诺跨平台严格“恰好一次”投递。**

## 8. 数据持久化设计

首版使用 SQLite，消息、路由和任务不得只放内存。主进程使用单一数据库写入通道，账号进程不直接修改数据库；数据库事务中不执行网络请求。SQLite 文件放本机磁盘，不放网络共享目录或实时云同步目录。[^sqlite]

### 8.1 最小五张业务表

| 表名 | 主要内容 |
|---|---|
| `accounts` | 本地账号编号、绑定 UID、显示名、启用状态、认证状态、最近活性时间 |
| `inbox_messages` | 原始客户消息、规范化字段、消息类型、源ID、源时间、收到时间、解析状态 |
| `feishu_outbox` | 发往飞书的客户转发、回复回执和告警任务，以及投递结果和飞书消息ID |
| `reply_tasks` | 本人飞书回复原文、原事件ID、冻结路由、发送状态、请求标识、错误与过期时间 |
| `sync_state` | 每个账号/会话的已同步位置、补拉范围、完成状态与未补齐缺口 |

建议关键约束：

```text
accounts.account_key：主键
accounts.expected_uid：启用账号之间唯一

inbox_messages：
  UNIQUE(account_key, account_uid, cid, source_message_id)
  只对取得可信源消息ID的正常消息执行此唯一约束

feishu_outbox：
  delivery_id：主键
  idempotency_key：唯一
  feishu_message_id：非空时唯一

reply_tasks：
  task_id：主键
  feishu_reply_message_id：唯一

sync_state：
  PRIMARY KEY(account_key, account_uid, cid)
```

`inbox_messages` 保存接收时的账号 UID 快照。`reply_tasks` 再保存该快照及 `cid`、客户 UID，不在执行时根据当前昵称或新的账号配置重建路由。

`feishu_outbox` 对客户转发任务关联 `inbox_message_id`；对回执关联 `reply_task_id`；只有“客户转发”类型可作为首版引用路由入口。

### 8.2 原子性与恢复

入站消息保存与飞书投递任务创建必须在同一事务完成。本人回复去重与闲鱼发送任务创建也必须在同一事务完成，避免重启后有消息无任务或同一操作出现两个任务。

飞书发送请求也应使用固定的投递身份；其 SDK 请求模型提供 `uuid` 字段。重试需依据官方接口的去重规则和有效窗口实施，不能每次生成新 UUID，也不能将平台短期去重当成永久保障。无法确认是否已投递的情况保留待核对状态。[^feishu-create]

任务、路由和补拉进度均可跨重启恢复。数据库不可写、磁盘满或映射损坏时停止新的客户发送，不能切换到纯内存运行来“凑合发”。

首版不自动删除仍可被引用的映射、未完成任务和异常记录。日志做容量轮转；完整数据保留期限和清理功能在实际使用后确定，清理后旧引用必须明确拒绝，不能猜路由。

## 9. 重连、补拉与离线边界

### 9.1 账号状态

至少区分 `STARTING`、`ONLINE`、`RECONNECTING`、`AUTH_REQUIRED`、`RISK_PAUSED`、`STOPPED`。账号 UID 不匹配属于必须人工处理的错误状态。

进程存活不等于闲鱼在线；本地发送过心跳也不等于服务端确认连接健康。在线判断应综合注册就绪、可验证的服务端活动或心跳响应、连接状态和最近错误；具体协议条件在首次联调确定。

网络错误使用指数退避与随机抖动重连。认证失败或风控异常进入人工处理状态，不能通过无限重连、高频 Token 刷新或自动清除风控状态“恢复”。

### 9.2 有界补拉

首次启用记录监控起点，只将起点之后的客户消息当成正常新消息；历史查询用于建立基线，不将旧聊天全部灌入飞书。

重连后从上次确认的同步位置开始，带少量时间重叠补拉，再按源消息ID去重。不能在重连时将当前时间直接写成“全部同步完成”。

补拉先刷新会话列表，覆盖离线期间新出现的会话，再补拉相关会话消息。只补拉已知客户会漏掉断线期间首次联系的新客户。

每次补拉设置会话页数、每会话消息页数、总时间和读请求速率上限。到达边界、接口不给完整历史、游标异常或解析失败时，保存缺口并在飞书显示“补拉未完整，请到闲鱼核对”，而不是无条件推进同步位置。

不把任意长时间离线后的完整历史恢复作为 MVP 保证。短时间断线补拉和新会话发现是实测项；未通过前不能把该工具当成唯一收消息入口。

### 9.3 闲鱼与飞书都要考虑离线

闲鱼侧离线期间无法实时接收，只能恢复后尝试补收。飞书事件连接离线期间，本人发送的回复不能假定一定会被平台完整重放。

首版不增加飞书聊天历史全量同步。本人提交回复后，必须看到带任务编号的回执，才知道消息桥已经接收；没有回执时先核对状态，不把飞书界面“发送成功”当成闲鱼回复已投递。

迟到的飞书事件以原 `create_time` 计算任务年龄，不能因为程序刚收到就重新获得完整有效期。首版拟定回复有效期为 10 分钟，超时提示重新确认，不自动发出几个小时前的回复。

### 9.4 告警能力的真实边界

某个闲鱼账号失效而电脑和飞书连接正常时，可以立即通过飞书告警；另外两个账号继续工作。

**电脑关机、整个程序退出或整机断网时，本地程序无法及时向飞书告警。** 主进程只能监督仍在本机运行的账号进程，不能通知自己的整机失联。首版恢复后发送离线区间、补拉结果和未确认任务摘要。

“没有收到告警”不代表系统一定在线。出门前查询一次状态；真正的整机离线即时告警需要独立外部监控，属于后续功能，不放入首版。

## 10. 限流与异常处理

上游的默认每分钟 1 次写入是本地实现，不是闲鱼官方承诺的安全额度。首版保留此保护，每个账号独立串行排队；三个直连账号共用网络出口，不意味着整体操作风险相互独立。[^limiter]

下列数值是本项目拟定初始配置，不是平台限制或已经测得的性能结论：

| 配置 | 首版建议 | 说明 |
|---|---|---|
| 每账号发送并发 | 1 | 防止乱序与重复领取 |
| 每账号写入上限 | 1 次/分钟 | 首版沿用上游默认，排队时明确反馈 |
| 未发送回复有效期 | 600 秒 | 以飞书原始消息时间计算 |
| 重连退避上限 | 30 秒 | 加随机抖动；认证/风控错误不走无限重连 |
| 每次补拉总耗时上限 | 60 秒/账号 | 超限记录缺口，后续按受限策略继续或人工核对 |
| 每会话单次补拉上限 | 5 页，每页最多 20 条 | 以实际接口支持为准，不无限翻页 |
| 告警方式 | 状态变化时通知 | 避免每次重试都刷屏 |

不把接收及时性与回复吞吐量混为一谈。客户消息可以即时进入飞书，但连续提交的多条回复可能因写入限制而排队；必须显示排队状态和账号归属。

| 异常 | 首版行为 |
|---|---|
| 飞书回复重复事件 | 返回已有任务结果，不重复创建发送任务 |
| 闲鱼同一消息重复到达 | 合并元信息，不重复推送正常客户消息 |
| 同一客户连续两句相同文字 | 根据不同源消息ID分别保留 |
| 引用丢失、映射缺失或冲突 | 拒绝发送，提示引用原客户转发消息 |
| 非本人或其他聊天的消息 | 拒绝，记录脱敏安全日志 |
| Cookie/Token 失效 | 暂停该账号，要求人工重新验证 |
| 账号 UID 不匹配 | 立即隔离该账号，不自动改绑 |
| 发送前明确连接失败 | 保持未发送状态，有限重试且受有效期约束 |
| 发出后超时或进程崩溃 | 标记 `UNKNOWN`，不盲目重发 |
| 平台明确拒绝/风控 | 告知原因，暂停相应操作；不自动解除风控 |
| 飞书消息投递不确定 | 用固定投递身份按平台规则处理；无法核对则保留未知状态 |
| 解析失败或缺少客户ID | 提示异常，不猜客户，不静默忽略 |
| 磁盘满或数据库失败 | 停止新发送，保留错误信息，恢复后检查任务状态 |

## 12. 最小 MVP 实施顺序

### 阶段 0：验证底层能力，不先搭大框架

只用一个测试账号，确认登录、监听、发送和历史查询在本地 Windows 环境可用。记录上游 commit、Python 和依赖版本，保存脱敏后的原始事件作为测试样本。

重点验证：正常文本的真实消息ID与时间、`new_msg` 补正文、客户 UID 与会话对应关系、收发连接是否互相影响，以及飞书手机端直接引用是否返回可用 `parent_id`。

使用本人控制的测试客户账号完成往返，不能随意向真实客户批量发测试消息。验证频率遵守限流。

**退出条件：一条完整消息能关联正确账号、客户、会话；能发出文字，并且发完后继续接收后续客户消息；飞书引用身份可验证。某项失败先修该项，不扩展三个账号或建设后台。**

### 阶段 1：先完成账号目录与直连底座

新增配置、`AccountPaths` 和 `NetworkProfile`，修复登录与刷新写回路径，隔离所有账号缓存。建立账号 UID 校验、禁用自动抓错浏览器账号的兜底，并接入直连连接创建入口。

首版只实现 `direct`；代理模式报未实现。建立主进程、账号进程和最小 SQLite 结构。

**退出条件：两个不同测试账号在目录和进程间不会覆盖登录态；故意给 A2 装入 A1 的凭据会被阻止；实际直连路径通过检查。**

### 阶段 2：跑通单账号飞书双向闭环

实现入站持久化、飞书转发、本人绑定、直接引用路由、发送任务、结果回执和双向去重。正文类型、账号/客户缺失、未引用、非本人等错误路径同时完成。

**退出条件：A1 客户发消息 → 飞书收到 → 本人引用回复 → 正确客户收到 → 飞书显示真实状态。程序重启后，旧转发消息仍可正确引用，重复事件不会重复发给客户。**

### 阶段 3：扩展到三个账号并补齐可靠性

启动 A1、A2、A3 独立进程，完成每账号发送队列、在线状态、错误隔离、有限重连、离线补拉和新会话发现。补齐发送超时、崩溃恢复、未知任务与过期任务处理。

**退出条件：三个账号并行收发不串号；同一客户联系两个账号时能分别回复；一个账号失效不影响其他账号；收发不确定时不会自动重复发送。**

### 阶段 4：本地常驻与最终验收

完善启动说明、配置检查、日志轮转、计划任务、自启与停止流程。进行持续运行和故障注入测试，记录实际时延与失败情况。

**退出条件：通过下一节验收清单，才交付“可带出门使用”的 MVP。单次往返成功只证明可行，不能代替三账号常驻验收。**

## 13. MVP 验收清单

以下数量和时延是拟定测试标准，不是当前已完成结果，也不是平台承诺。所有真实发送测试分散执行，遵守每账号发送限制；失败路径尽量使用模拟回包和脱敏回放。

| 测试 | 合格标准 |
|---|---|
| 三账号收消息 | 每个账号至少完成 5 条文本接收，全部展示正确账号ID、客户ID和正文 |
| 三账号回复 | 每个账号至少完成 3 次飞书引用回复，目标会话全部正确 |
| 同客户跨账号 | 同一测试客户联系 A1、A2，分别引用回复，目标账号不互换 |
| 不同客户同名 | 路由只使用 ID，不按昵称错误合并 |
| 相同正文 | 同一客户的两条不同源消息ID、相同正文都能保留 |
| 飞书重复事件 | 同一飞书消息事件重复投递多次，只生成一个闲鱼发送任务 |
| 错误引用 | 未引用、引用状态通知、引用自己的回复均不能触发发送 |
| 未授权操作 | 非绑定本人、非绑定私聊的事件不能触发发送 |
| 程序重启 | 映射与未发送任务可恢复；发送中任务进入待核对而非直接重发 |
| 发送结果不明 | 模拟发出后超时，只标记 `UNKNOWN`，不自动补发第二条 |
| 单账号认证故障 | 故障账号暂停，其他账号继续；飞书可用时及时告知 |
| 有界断线恢复 | 测试断网 1～5 分钟，包括离线期间新客户；恢复后补收或明确报告缺口 |
| 自发消息回流 | 已发回复不再次被当成客户新消息推送 |
| 非文本与异常包 | 能提示已识别类型或异常，不能静默丢弃已知客户事件 |
| 队列过期 | 超过有效期的回复不自动发出，飞书收到重新确认提示 |
| 直连验收 | HTTP、WebSocket、登录路径分别验证；不依赖仅看浏览器查 IP |
| 本地持久化故障 | 数据库不可写时拒绝新发送，不绕过持久化保护 |
| 持续运行 | 三账号至少持续运行 24 小时并记录中断、重连、补收与任务状态 |

接收时延建议先以“多数正常文本在本地收到闲鱼事件后 5 秒内被飞书发送接口接受”为目标，并记录从测试客户发送到飞书实际可见的端到端时延。手机系统通知出现时间还受设备和飞书通知设置影响，不能仅凭本地接口成功推算。

正式验收记录要区分真实账号测试、模拟测试和未测试项目。**不串号是硬门槛；未知发送不盲重试是硬门槛；不能用整体成功率掩盖这两类错误。**

## 14. Windows 常驻运行与安全边界

本地电脑必须持续开机、联网并关闭自动睡眠；锁屏可以作为常驻方式，但需实际测试。不要将注销用户与锁屏混为一谈。首版建议使用固定 Windows 用户登录后运行，通过计划任务实现自启和失败重启，验证后台身份对凭据、目录和网络的访问。

Windows 多进程启动要使用安全的主入口，并适配 `spawn`，避免子进程重复启动主服务；同时设置单实例锁，防止手动启动和计划任务各运行一套系统。[^python-process]

账号凭据只保存在本地受限目录，按实际 Windows ACL 限制访问；飞书消息只包含业务所需信息，不携带 Cookie、Token 或密钥。客户消息被转发到飞书意味着飞书也保存了一份客户内容，不能称为“所有数据完全不离开本机”。

原仓库的 Cookie 加密密钥由主机名和用户名派生，不能据此把文件当成无需保护的普通数据。继续按敏感凭据管理，不将这种机制视为抵御本机恶意程序的强安全边界；跨机器迁移也不能假定直接复制就能解密。[^crypto]

消息正文一律作为数据处理，不执行客户指令，不拼接 Shell 命令，不触发任意工具调用。诊断日志默认不记录完整正文和完整原始协议包；调试样本必须脱敏，严禁把认证字段提交到仓库。

程序仅用于本人授权的三个自有账号，不处理交易、付款、改价或商品发布。遇到验证和风控交由本人处理；仓库本身也明确了自有账号使用与不绕过风控的边界。[^repo]

## 15. 后续代理扩展，不阻塞 MVP

### 15.1 首版预留内容

首版只需具备账号级 `network` 配置、集中创建 HTTP/WebSocket/浏览器连接的入口、直连实现，以及对未支持模式的明确报错。不要采购代理，不做代理管理页面，不为尚未使用的代理池建设调度系统。

### 15.2 需要独立出口时再实现

后续将每个账号配置切换为独立固定代理：

```text
A1 → 固定代理 A → 出口 IP-A
A2 → 固定代理 B → 出口 IP-B
A3 → 固定代理 C → 出口 IP-C
飞书连接 → 独立网络配置，不跟随闲鱼账号切换
```

代理扩展必须覆盖 HTTP 接口、WebSocket 初次连接与重连、扫码登录和浏览器刷新。具体代理能力按 Requests、websockets 及浏览器运行库的正式接口实现；不能以浏览器配置代理代替 Python 客户端代理。[^requests][^websockets]

代理模式故障时暂停对应账号，**不得自动退回本地直连，也不得借用另一个账号的代理**。需要严格防止直连泄漏时，再增加操作系统出站限制。

三个代理地址或三个端口不等于三个公网出口。后续必须分别验证实际出口，并做断代理测试；共用一台 VPS 的不同入口端口若最终走同一出口，就没有实现出口 IP 隔离。

公网 IP 隔离只说明网络路径不同，不等于设备隔离、身份隔离，也不保证账号不会被平台关联或触发风控。本项目不提供绕过平台检测的设计。

代理之外的后续功能可以包括图片转发、会话分组、简易操作面板、整机外部存活监控；均在文本双向闭环稳定后按实际需要增加，不预先纳入首版。

## 16. 开发交付要求与最终结论

交付应包含：可运行的三账号消息桥代码、锁定依赖、配置示例、逐账号登录与飞书绑定流程、数据库初始化/升级脚本、脱敏测试样本、自动测试、Windows 常驻说明，以及真实联调与未验证项目记录。以上随同一个项目交付，不另外搭建后台平台。

开发期间固定以下约束：**三账号全部直连；代理仅预留；一个飞书机器人；一个授权操作人；只接受直接引用的纯文本回复；固定映射不猜目标；结果不明不自动重发；每完成一个阶段再扩展下一阶段。**

**最短落地路径：先验证单账号协议和手机引用事件 → 完成账号目录与直连底座 → 跑通单账号飞书双向闭环 → 扩展三账号与故障恢复 → 验收本地常驻。**

最终 MVP 不是“闲鱼运营平台”，也不是“AI 客服系统”，而是一个可靠的小工具：**让三个闲鱼账号的客户消息出现在同一个飞书入口，并把本人回复准确送回原账号、原会话、原客户。**
